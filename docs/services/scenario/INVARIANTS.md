# scenario: инварианты

| Правило | Где держится |
|---|---|
| Опубликованные версии неизменяемы, исправление это новая версия | [AsyncpgScenarioRepository](../../../backend/src/scenario/adapters/asyncpg.py): версии только вставляются, у существующих меняется лишь `active` |
| Активна не больше одной версии | частичный уникальный индекс `scenario_versions_one_active` в [001_init.sql](../../../backend/migrations/001_init.sql) |
| Номер новой версии это `max + 1`, номера не переиспользуются, откат номер не уменьшает | `publish` под advisory-блокировкой; после отката на 1 следующая публикация получит `max + 1`, а не 2 |
| Версия попадает в хранилище только после `parse_scenario` и `validate_scenario` без проблем | [ScenarioService.publish](../../../backend/src/scenario/services.py) |
| Невалидная публикация ничего не меняет: ни активную версию, ни черновик | `ScenarioInvalid` бросается до записи |
| `ScenarioMalformed` из парсера превращается в `ScenarioInvalid` с одной проблемой `malformed`, `step_id = ""`, текст берётся из исключения | `publish`: черновик может быть любым JSON |
| Черновик один, может быть невалидным, `revision` растёт на каждое сохранение | таблица `scenario_draft` (`CHECK (id = 1)`) |
| `save_draft` атомарен: `UPDATE ... WHERE revision = $base`; ноль строк это `DraftConflict`. Из N параллельных сохранений с одним `base` проходит ровно одно | `AsyncpgScenarioRepository.save_draft` |
| Публикуются данные черновика как есть (сырой JSON); `rollback` копирует в черновик данные версии в том виде, как они хранятся | `activate_version` |
| `rollback(n)` = одна операция порта `activate_version(n)`: в одной транзакции под блокировкой версий активной становится `n` и черновик заменяется её данными, `revision` растёт. Сбой на любом шаге откатывает всё (активная версия прежняя, черновик не тронут). Несуществующая `n`: `NotFound` | [AsyncpgScenarioRepository.activate_version](../../../backend/src/scenario/adapters/asyncpg.py), проверено тестом с ограничением на `scenario_draft` |
| Сид пишется один раз и только в пустую таблицу версий, повторный вызов ничего не делает | `seed` под той же блокировкой, что и публикация |
| `Scenario.version` берётся из номера строки, а не из JSON: в данных версии номера нет | `parse_scenario(data, version)` |
| Кандидат на публикацию разбирается с версией 0: настоящий номер известен после записи | `_CANDIDATE_VERSION` |
| Порядок `list_versions`: по возрастанию номера | оба адаптера |
| Конец анкеты только `finish: true`, других способов закончить нет. `info` без `next` и без кнопок с переходом это `missing_next` | `_needs_next` в [validator.py](../../../backend/src/scenario/validator.py) |
| `@return` не достижим при пустом стеке возврата. Пуст стек от `entry` и после кнопки под финалом, которая начинает новый проход. Вложенный `Call` без `then` наследует возврат внешнего вызова | `_check_returns`, `_can_return` |
| Текст, подпись и `url` проходят те же ограничения, что у Telegram: непустой текст до 4096 единиц UTF-16, непустая подпись, адрес `http(s)` без пробелов | `_check_text`, `_check_option` |

## Ограничения

- Замена черновика при откате безусловна: редактор, державший старый `base_revision`, получит `DraftConflict` на следующем сохранении, это ожидаемо.
- Пределы длины id, подписи и `callback_data` проверяет только валидатор, движок их не проверяет.
