# leads: инварианты

| Правило | Где держится |
|---|---|
| У чата не больше одной открытой (`partial`) заявки | частичный уникальный индекс `leads_one_partial_per_chat` ([001_init.sql](../../../backend/migrations/001_init.sql)) |
| `upsert_open` обновляет открытую заявку чата с тем же `id` и прежним `created_at`; иначе вставляет | [asyncpg.py](../../../backend/src/leads/adapters/asyncpg.py): транзакция с advisory-блокировкой на чат, `UPDATE ... WHERE status = 'partial'`, при отсутствии строки `INSERT` |
| Заявка `full` не перезаписывается никогда. Новый проход после финала даёт новую запись | то же: `UPDATE` трогает только `partial`; `full` индекс не затрагивает |
| `finish` на чате с открытой частичной заявкой превращает её в `full` (тот же `id`); без неё вставляет новую `full` | [services.py](../../../backend/src/leads/services.py) |
| Сначала запись, потом уведомление | `LeadService._save_and_notify` |
| Статус заявки задаёт метод сервиса (`save_partial`/`finish`), а не поле, пришедшее от вызывающего | `dataclasses.replace` в сервисе |
| `get` несуществующей заявки это `NotFound` | оба адаптера |
| `list(status)` отдаёт новые первыми (`created_at`, затем `id` по убыванию) | оба адаптера |
| Подпись ключа `name` это «Имя» (R9); остальные ключи показываются как есть | `display_key` в [formatter.py](../../../backend/src/leads/formatter.py) |
| Текст для менеджера без разметки Telegram (`parse_mode` не задаётся): значения вводит пользователь | `format_lead`, `ManagerNotifier` |

## Формат текста

Строки по порядку: `Новая заявка` или `Частичная заявка`; `Направление: <branch>` если не пусто; `Telegram: @<username>` если есть; `Последний шаг: <last_step>` для partial, если есть; затем `<ключ>: <значение>`. Части режутся по границе строк, строка длиннее 4096 символов режется жёстко (между кусками такой строки перевода строки нет). Соединив части через `\n`, получаем исходный текст, кроме жёстко разрезанных строк.

## Логи

Только `lead_id` и `status`; телефоны, имена, значения ответов в логи не попадают.
