# dialog: решения

## Движок как чистая функция

- Решение: `step(scenario, session, event) -> StepResult`, всё состояние в `Session`, ввода-вывода нет.
- Альтернатива: класс с состоянием и обращением к хранилищу.
- Почему: сценарий меняется в редакторе, прохождения нужно проверять тестами по спискам подписей (см. `tests/utils/walker.py`), а сессия сериализуется целиком.

## "Назад" через снимки

- Решение: `history_returns` и `history_answers` параллельны `history`; назад возвращает стек и ключи ответов на момент ухода с шага.
- Альтернатива: удалять ответ того шага, с которого ушли назад.
- Почему: при удалении только одного ответа в заявке оставались ответы брошенной ветки. Снимок ключей оставляет в заявке то, что человек реально прошёл, а ответы "хаба", куда возвращаются многократно, продолжают накапливаться.

## Финал с кнопками и `back_to`

- Решение: `Step.finish`, кнопка под финалом начинает новый проход с чистыми ответами; `Step.back_to` задаёт, куда ведёт "Назад" на первом шаге прохода.
- Альтернатива: возврат на финальный шаг.
- Почему: ответы очищены, а текст финала подставляет `{name}`: возврат показал бы шаблон без значения. Спецификация требует "Назад" на каждом шаге.

## Сессия как JSON

- Решение: `session:<chat_id>` хранит JSON; сериализатор в `adapters/redis.py`, при чтении кортежи и `Answer` восстанавливаются.
- Альтернатива: pickle, либо хэш Redis по полям.
- Почему: JSON читаем глазами при разборе жалоб и переживает изменения кода; pickle небезопасен и привязан к модулям. Хэш усложнил бы вложенные `answers` ради поля, которое всегда читается целиком.
- Цена: поле, добавленное в `Session`, обязано попасть в сериализатор и получить значение по умолчанию при чтении, иначе сессии старого формата сломаются.

## Напоминания в ZSET

- Решение: ZSET `reminders` с оценкой по времени срабатывания; `due` читает диапазон до `now`.
- Альтернатива: TTL-ключи и подписка на истечение.
- Почему: истечение ключа ненадёжно доставляется, а `ZRANGEBYSCORE` с `limit` даёт пакет по запросу задачи раз в минуту.
