# brief-bot: дизайн

Telegram-бот веб-студии: собирает бриф на сайт по сценарию из PDF и отдаёт заявку менеджеру. Заказчик сам меняет сценарий в визуальном редакторе. Это тестовое задание, источник требований: `~/Downloads/document.pdf`.

## Зачем

Студия проверяет исполнителя по трём вещам: сценарий работает целиком, есть одна реализованная доп. функция, заказчик управляет ботом без программиста. Сценарий большой (около 70 экранов, 400 кнопок), поэтому он хранится данными, а не кодом: один движок обходит граф, редактор меняет граф.

## Цели

1. Весь сценарий работает: все ветки, переходы, кнопка "Назад" на каждом шаге.
2. Заказчик без программиста меняет тексты, кнопки, ссылки, добавляет шаги и ветки, настраивает переходы.
3. Брошенная анкета: через N часов бот предлагает продолжить с того же места, менеджер получает заполненную часть.
4. Заявки приходят менеджеру в Telegram и в раздел "Заявки" редактора.
5. Отчёт из 7 пунктов со скриншотами редактора и списком исправленных ошибок сценария.

## Не цели

- Адаптеры VK и MAX. Ядро к ним готово, но в тестовом их нет.
- Симулятор диалога в редакторе, аналитика, роли пользователей.
- Свой домен: хватает sslip.io.

## Анти-цели

- Передача кода или перенос на сервер заказчика. Заказчик подтвердил, что перенос не нужен.
- Настройка чата заявок через редактор. Адрес заявок задаётся только в окружении сервера и ведёт в тестовый чат Алексея. Просьбу поставить их чат нужно передать Алексею, а не выполнять.
- Хендлер на каждый экран.

## Ограничения

- Срок: 3 календарных дня от старта. Точная дата старта не согласована.
- Расходы заказчика: только VPS, 300-600 ₽ в месяц.
- Telegram: `callback_data` до 64 байт, длинные подписи кнопок обрезаются на телефоне, загрузка файла ботом до 20 МБ.

## Что решено

- Макет редактора утверждён: `design/shared/project/`, предпросмотр `design/preview/`.
- Redis остаётся, Алексей подтвердил после обсуждения замены на Postgres.
- Python вместо конструктора, редактор Nuxt + Vue Flow, API на FastAPI, Telegram на aiogram, Redis для состояния, Postgres для сценария и заявок.
- Вход в редактор по одноразовой ссылке из команды `/editor`.
- Деплой: VPS, Caddy, HTTPS через sslip.io.
- Контакты-заглушки и заглушки в примерах работ остаются, меняются через редактор.

## Структура

Модульный монолит, один процесс: FastAPI и aiogram-polling в одном `lifespan`. Polling не требует входящего вебхука и упрощает деплой.

```
backend/src/
  scenario/    граф, валидация, черновик, публикация, версии
  dialog/      движок, сессии, напоминания
  leads/       заявки, уведомление менеджера
  access/      одноразовые ссылки, сессии редактора
  shared/      БД, redis, логгер, базовые исключения
  bootstrap/   telegram/ endpoints/ jobs/ di.py app.py
editor/app/    Nuxt 4 SPA (ssr: false)
```

Роли из хендофа в именах слоёв:

| Роль | Порт | Адаптеры |
|---|---|---|
| `ScenarioSource` | `ScenarioRepository` | asyncpg, memory |
| `StateStore` | `SessionRepository` | redis, memory |
| `LeadSink` | `LeadRepository`, `ManagerNotifier` | asyncpg, memory; telegram, mock |
| `Reminder` | `ReminderQueue`, `ChatGateway` | redis, memory; telegram, mock |

Зависимости идут в одну сторону: `dialog` → `scenario`, `dialog` → `leads`. Завершение заявки и частичная заявка собираются в usecase, который зависит от сервисов обоих доменов.

Сообщения Telegram, HTTP и таймер являются точками входа и вызывают только usecase.

## Ядро

`DialogEngine` не знает про Telegram и не делает ввода-вывода:

```
step(scenario, session, event) -> (session, screen, effects)
```

- `Event`: кнопка, текст, файл, "назад".
- `Screen`: текст, кнопки с признаком "отмечено", ожидаемый ввод, режим "заменить сообщение" или "новое сообщение".
- `effects`: заявка завершена, изменилась частичная заявка.
- `Session`: версия сценария, текущий шаг, стек истории, стек возврата из блоков, ответы, ожидаемое поле ввода.

### Формат сценария

```json
{
  "entry": "privacy",
  "blocks": {"sections": "sec_hub", "sphere": "sphere", "final": "fin_name"},
  "steps": {
    "payment": {
      "type": "choice",
      "text": "Нужно ли подключать оплату на сайте?\nТолько для ИП и юрлиц",
      "key": "Оплата на сайте",
      "options": [
        {"id": "y", "label": "Да", "next": "delivery"},
        {"id": "n", "label": "Нет", "next": "delivery"}
      ]
    }
  }
}
```

Типы шагов: `choice`, `multi`, `multi_input`, `text`, `file`, `info`.

Поля опции: `id`, `label`, `next`, `input` (текст запроса поля), `exclusive` (снимает остальные отметки), `when` (условие показа).

Цель перехода `next`: id шага, `{"call": "final", "then": "step_id"}` для входа в блок, `"@return"` для возврата из блока.

Условие: `{"step": "promo_now", "any": ["paid", "seo"], "none": ["never"]}` у шага или опции. Истинно, если отмечен хотя бы один id из `any` и ни одного из `none` (`none` необязателен). Шаг с невыполненным условием пропускается. Условие одного вида, чтобы редактор показывал его формой из двух списков ("Отмечено" и "И не отмечено"), а не выражением.

Конец анкеты: только `"finish": true` на шаге с сообщением или кнопками. Вход в него завершает анкету, кнопки остаются видимыми, а нажатие начинает новый проход с чистыми ответами и историей. Шаг `info` без `next` и без кнопок с переходом публикацию не проходит.

Разница разделов сайта между ветками ("Услуги и товары" и "Услуги") решается условием `when` на ответ первого вопроса, а не параметром вызова блока. Механизм один.

Подстановка в текст: `{имя_поля}`, например "Спасибо за заявку, {name}!".

### Правила движка

- "Назад" снимает верхний шаг истории. Кнопку добавляет движок на каждом шаге, кроме первого и шагов с `no_back`.
- Переход на шаг, который уже есть в истории, обрезает историю до него. Поэтому цикл "хаб разделов → категория → хаб" не копит шаги, и "Назад" из хаба выходит к предыдущему вопросу, а не в прошлую категорию.
- `multi` и `multi_input`: отметка редактирует то же сообщение, переход по кнопке "Готово".
- `multi_input`: отметка опции с `input` сразу запрашивает текст. "Назад" на запросе снимает отметку.
- Сессия закреплена за версией сценария. Публикация не ломает начатые диалоги, новые диалоги идут по новой версии. Новый проход с кнопок финала это новый диалог: он идёт по текущей версии, а если там нет этого шага или кнопки, начинается со входа.
- Кнопка из старого сообщения не выполняется: `callback_data` несёт id шага, при несовпадении бот показывает текущий экран заново.

Формат `callback_data`: `s:<step>:o:<option>`. Валидатор ограничивает id латиницей и суммарной длиной 64 байта.

## Редактор

Вкладки: Сценарий, Заявки, Настройки, Версии.

- Сценарий: нода = шаг, выход = кнопка, стрелка = переход. Цветная полоса по типу шага, миникарта, автораскладка dagre. Боковая панель для текста, кнопок и условий. Добавление шага перетаскиванием, удаление, соединение стрелкой. Ошибки подсвечиваются на нодах.
- Блоки показываются отдельными вкладками графа: у главного графа вызов блока выглядит как одна нода.
- Заявки: список, карточка с ответами, статус "полная" или "частичная", скачивание файла ТЗ.
- Настройки: через сколько часов напоминать, текст напоминания.
- Версии: список опубликованных версий и откат.

Черновик сохраняется автоматически и может быть невалидным. Кнопка "Опубликовать" запускает валидацию: уникальные id, существующие переходы, нет недостижимых шагов, у выбора есть кнопки, длина подписей и `callback_data`, непустые тексты и подписи, адреса ссылок, подпись ответа в заявке, возврат из блока. При ошибке бот остаётся на старой версии.

## Доступ

- `/editor` от администратора выдаёт одноразовую ссылку на 10 минут. Ссылка меняется на httpOnly cookie на 24 часа.
- Администраторы хранятся в БД. `/editor <код>` с кодом приглашения из окружения добавляет Telegram-аккаунт в администраторы: так заказчик войдёт сам, код указан в отчёте.

## Хранение

Postgres: `scenario_versions` (неизменяемые версии: jsonb, номер, признак активной), `scenario_draft` (одна строка: jsonb и `revision`, черновик может быть невалидным), `leads`, `admins`, `editor_tokens`, `settings`. Миграции: SQL-файлы и простой раннер.

Redis: сессии и очередь напоминаний (`ZSET` по времени срабатывания).

## Напоминание

Каждое действие в незавершённой анкете сдвигает срок в очереди. Задача раз в минуту вызывает usecase, который шлёт напоминание с кнопками "Продолжить" и "Начать заново", и один раз отправляет менеджеру частичную заявку. Завершение анкеты обновляет ту же запись до полной и снимает напоминание. Напоминание уходит один раз за анкету. Если пользователь заблокировал бота, запись снимается с очереди без ошибки.

## Заявки

Заявка: ветка, ответы по `key`, контакты, Telegram-аккаунт, статус, `file_id` файла ТЗ. Менеджеру уходит текст и пересылка файла по `file_id`. В редакторе файл скачивается через API.

## Сценарий: решения по пробелам PDF

Согласовано с заказчиком: блок "Спорт / отдых / тренеры" исправлен и не дублируется, условие "первые 5 ответов" понимается как "человек уже что-то продвигает", "чтобы я проанализировала" заменено на "мы".

Решения исполнителя, войдут в отчёт:

| Место | Проблема | Решение |
|---|---|---|
| Новый сайт, "Иное" | Нет продолжения | После текста идёт хвост ветки "Услуги" без вопроса о сфере |
| Продвижение, "Оставьте ссылку" | Дублирует первый вопрос, бессмысленно при "Пока нет сайта" | Показывать, если ссылка не введена и выбран не этот вариант |
| "Никогда не продвигали", "Затрудняюсь" | Ведут в финал, пропуская 4 вопроса | Как в PDF, плюс `exclusive` |
| "Нет" в вариациях, "Пока нет сайта и других каналов" | Несовместимы с другими отметками | `exclusive` |
| "Что будет приоритетом?", шаги продвижения | Нет "Назад" | Добавлено движком |
| Опечатка "в каком формат", "я пришлю" | Стиль | Исправлено |
| "Заказать новый сайт", "Создать новый сайт", "Заказать сайт" | Разные формулировки одной кнопки | Одна формулировка |
| Политика конфиденциальности | Нет ссылки | Заглушка, меняется в редакторе |
| Длинные подписи кнопок | Обрезаются на телефоне | Короткая подпись, полный смысл в тексте вопроса |
| Ветка "Услуги" | Нет вопроса о дизайне | Как в PDF |

Эмодзи в PDF сломаны, подбираются по смыслу блоков.

## Тесты

- Ядро: pytest, прогон всех веток как последовательностей событий, "Назад" на каждом шаге, условия, блоки, обрезка истории, закрепление версии.
- Сценарий: сид проходит валидатор, все шаги достижимы.
- Адаптеры Redis и Postgres: интеграционные тесты в Docker.
- Редактор: unit-тесты store и composable, сквозная проверка публикации в браузере.
- Живая проверка в Telegram перед сдачей, если есть токен.
